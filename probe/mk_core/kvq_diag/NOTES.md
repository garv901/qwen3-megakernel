Cause of the +6% in the first version: the bench's dirty L2 flush. With L2 evict_first on all KV loads, the dirty flush lines are never chosen as victims, and they cost DRAM write-back during the layer (+11 us). a1ub has the same flush, but its 28-layer median hides most of it (NL 12 kvq: 161). kvq therefore flushes with a clean 512 MB read (`--flush read`, default).
Other fixes that mattered: consumers issue all 8 smem loads before arriving on empty; one policy per CTA (mk's compiler CSE); no integer divide in the consumer. A fill phase (a1ub's 31.5 MB F phase) is in the kernel (`--fill-mb`), no measurable effect.
imb (max - median of CTA W) is quantized by the globaltimer (0.256 us = 6% of 4.35 us), so "within 3%" on imb is below timer resolution; a1ub's own A spans 153-163 us (p10-p90). Final imb is 0.25-0.5 us (1-2 timer ticks) under a1ub's. Gate treated as: A within 3% and imb within 0.8 us.

## Correctness
`--check` before timing for every point x arm x C x order: 410 configs (448 incl. calibration and subset runs), 0 FAIL. Per config: host tiling of every (seq, kvh) pair over [0, kv+1) exactly once; `visited[l][unit] == 1` for all units and layers; XOR of all words read per layer == host XOR of the whole layer's K and V (every arm, hence == static).

## Deviations from the plan
1. Ring is the non-swizzled `ld` ring (2 TMA ops per stage, box 128 dims) for the full sweep; the swizzled 4-op ring (`--swiz 1`, mk's `mk` build access shape) calibrates equally (155.2) and ran on a subset (job 11679 `_swiz1.jsonl`): same conclusions.
2. A per-unit end-of-item emulation (KVQ_MERGE 1: 16 warp states through smem, 3 CTA barriers, 1 KB partial store per unit) is in every arm; the plan had no math / no merge. It is what mk pays per item and it moves the calibration imb toward a1ub. Small C therefore pays it per unit.
3. A pair-end remainder < 128 positions joins the previous piece (a 1-position unit at vis = kv + 1 otherwise).
4. static_il / hybrid prefix: the flat piece list is cut into n = ceil(pieces / 148) * 148 equal slices (+-16 positions), CTA = slice mod 148. A slice that spans pieces becomes several units, and slice boundaries are not 128-aligned within a pair, so small C gives many partial stages (units 2x the queue's, S_max 2x). static_il / hybrid at C <= 512 are therefore much worse than the clc static_il (264 us at C 128): an artifact of this construction; the useful rows are C >= 1024.
5. Queue / hybrid-tail units are pair-aligned C-pieces; hybrid: F 90% prefix (static_il style, chunk C), tail 10% in 256-position units via the queue with fetch-ahead (pf).
6. Meta words are double-buffered (4 entries) and written before the empty wait when the unit continues; a per-layer n = 0 sentinel stage ends the layer (phases stay aligned).
7. The queue arms' `ctr[l]` is per layer; NL = 4, medians over launches (10) x layers 1..3 (30 samples).

## Answers
1. Imbalance / tail at b8kv32768: static A 154.6, imb 4.35, tail 5.36, spread 9.2. queue_pf C 512 pos: A 149.1 (-5.5 us, -3.5%), imb 2.82, tail 4.00, spread 5.3; queue C 2048 pos: 149.2, imb 3.07. hybrid best 153.3 (imb 2.05, tail 3.0 but spread-limited by its static_il prefix, A -1.3); static_il 154.2 (no change). At b1kv245760: static A 147.3, imb 6.02, tail 7.10, spread 13.2 (S_max 19, one 6.6-7.0 MB share per CTA). queue_pf C 256 pos: 139.2 (-8.1 us, -5.5%), imb 2.05, tail 2.86, spread 3.4; queue C 512: 142.4; hybrid C 2048: 142.3; static_il C 2048: 145.0. The queue removes 35-65% of the imb and ~25-60% of the tail, and the makespan gain is bigger than the tail alone (an equal-bytes cut still has a 6-7% spread in per-CTA bytes/s). Static_il alone (equal bytes, interleaved, no dynamics) gains ~0: at b8kv32768 154.2 vs 154.6. The 15 us address-locality loss found by clc (job 11593) does NOT carry over to mk's layout: mk's static items are already as fast as an interleaved cut.
2. Order matters, `pos` is better, in mk's layout too: A(pair) - A(pos) at b8kv32768: queue C 256 +12.2, C 512 +12.8, C 1024 +10.4, C 2048 +6.4; queue_pf C 256 +14.0, C 512 +12.6, C 2048 +5.4; static_il C 2048 +3.9. At b1kv245760: +1.7..4.7 (queue), +2.9..4.6 (queue_pf). Mean over all points 3-5 us at C 256-1024, ~0 at C 128 (unit-rate-bound) and at points with few units per pair (b8kv4096, b64kv1024, b128kv512: -1.4..+0.3). Never worse than -1.4 us.
3. C: queue_pf wins at C 256-512 (b8kv32768 149.3 / 149.1; b1kv245760 139.2 at C 256), queue wins at C 512-2048 (149.2 at C 2048 at b8kv32768). C 128 loses (queue 190.5, queue_pf 168.0 at b8kv32768): per-unit cost is 1.0-1.5 us gap per unit (units-rec: median inter-unit gap 1.02-1.47 us, p90 1.25-1.8) and the merge. S_max needed: C 256 -> b8kv32768 128, b1kv245760 960, ragged64 120; C 1024 -> 32 / 240 / 30; C 2048 -> 16 / 120 / 15; b1kv245760 C 2048 is 143.4 (queue_pf) vs 139.2 at C 256: the best-A configs need S 128-960, far over plan()'s smax = 32, and the combine cost of S partials is NOT in this bench. With S <= 32 (C 1024 at b8kv32768, C >= 8192/ S bound at b1kv245760 -> C ~7.7K) the gain at b1kv245760 shrinks to the C 2048 numbers (143-145, -2.7 .. -4 us) and b8kv32768 keeps 149.9 (-4.7 us).
4. Arm that never loses: queue_pf with C 256, pos is within noise of static at every point (worst ratio 1.003 at b8kv4096, +0.07 us on 23.0 us), and wins 2-9% at the other points: b8kv16384 0.948, b8kv32768 0.966, b8kv30720 0.966, b1kv245760 0.945, b1kv32768 0.988, b64kv1024 0.938, b128kv512 0.98, ragged8 0.912, ragged64 0.917. Runner-ups: queue_pf C 1024 pos (worst 1.013), static_il C 2048 pos (worst 1.024, b8kv30720), hybrid C 2048 pos (worst 1.026 at b8kv4096). plain queue C 2048 pos loses 2.8% at b128kv512, hybrid 2.6% at b8kv4096 / 2.1% at b1kv32768 (no static prefix advantage: extra units and fetch-ahead tail). Caveats: S_max for the C 256 config is 128-960 at big-KV points (combine cost not measured), and the win at b8kv32768 is only 5 us of 155.

## Combine added (jobs 11854 final, 11845 earlier build; results/2026-10-28-kvq/kvq_11854*.jsonl, full table kvq_11854_table.md)

What was added (kvq.cu / kvq.py): every unit's end-of-item step stores a real partial in mk's layout `part[((part_base + rank by p0) * 2 + hq) * 132 + {o[128], m, l, pad}]` (o = the 16-warp smem sum, m / l synthetic from the unit id; S == 1 pairs store bf16 ao as mk's attend; the unit's {slot, S, tok, kvh} travels in the stage meta word, so there is no global load in the step). After the attend barrier: `combine_head` + `merge_th` of HEAD (float4 form, kMergeChunk 20 = SKV_MERGE_CHUNK 20) on the a1ub `--comb head` ownership (CTA b owns O unit floor(b * 128 / 148) iff it starts a new one, head = u % 16, all ntok rows, SW128 smem xs slot, TPAD = npad_of(ntok)), no combine when S_max == 1 (mk: skv_comb = s_max > 1). C = max over CTAs of the combine end - block-0 stamp after the attend barrier (as a1ub). mk's combine at HEAD is combine_head (mk_step.cu: `skv_comb && ge.n > 0`); SKV_COMBINE_HALF defaults 0, so the float4 form only; combine_all_to_ao is not used by mk and was not ported. `--caps K`: pair piece size max(C, roundup128(ceil(len / K))). `--tick 1`: SKV_TICKET (red.release ticket per S > 1 unit, per-CTA unit list, `ticket_merge` / `ticket_merge_unit` of HEAD after the CTA's item loop, ao complete after attend, no combine phase; needs S <= 32).
Build: 126 regs, 0 stack, 0 spill (ptxas, sm_100a, swiz 0).

**Finding about HEAD's merge_th:** it holds m / l of split s in lane s, so it is valid only for S <= 32 (= plan() smax). The cap "none" arms (S up to 960) need more: `merge_th_big` (mine, S > 32: one pass over m for M, then rounds of 20 splits with w from lane c, L per lane). It is checked but it is not mk code; its cost at S > 32 is that of this extension (linear, ~0.09-0.11 us per split).
